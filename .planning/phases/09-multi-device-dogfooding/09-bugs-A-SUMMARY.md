# Phase 09 Plan bugs-A: Login UX + force_password_change Enforcement Summary

Surface the local email+password form on /login when the server reports local_enabled=true, and enforce User.force_password_change inside the SPA via a route guard in (app)/+layout.svelte plus a server change-password handler that returns the updated user.

## Tasks Completed

- Bug 1 — login surface: rewrote /login to render local form as primary view when local_enabled=true, kept Entra button when oidc_enabled=true, and showed both with a divider when both are enabled. Removed the hidden "Admin" toggle button. Commit 7f07cdb.
- Bug 4 — force_password_change enforcement: added the field to the User interface, added a \$effect-based route guard in (app)/+layout.svelte, taught changePasswordHandler to return the updated user, and made the SPA refresh the currentUser store and redirect to / on success. Commit 7aaf3eb.

## Decisions Made

- The local form is rendered as a primary surface, not hidden behind a corner-button. Bootstrap deployments (admin@localhost / trasker-admin) need a discoverable login.
- The route guard lives in the (app) layout, not in (app)/+layout.ts. SvelteKit static-export does not run +page.ts/+layout.ts on every navigation in the browser, so a $effect inside the layout component is the right reactive surface. The guard reads `isAuthenticated` and `currentUser` directly from `$lib/stores/auth`.
- /auth/change-password sits outside the (app) route group on purpose: the guard inside (app) cannot redirect there from there, so no loops are possible.
- Server change-password now returns the updated user (id, email, display_name, role, force_password_change). The handler reuses the *User returned by Store.UpdateUserPassword, which already runs `force_password_change = false` in SQL, so the response truthfully reflects the post-update row.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical functionality] Server change-password handler did not return the updated user**
- **Found during:** Bug 4 implementation
- **Issue:** Brief stated "On 200, server returns updated user (force_password_change should now be false). Refresh user store and redirect to /". The existing handler returned only `{status: "password changed"}`, so the SPA could not refresh its store without an extra round-trip — and any failure to refresh would leave force_password_change=true in the store, causing the route guard to bounce the user straight back to /auth/change-password.
- **Fix:** changePasswordHandler now returns `{status, user}` where `user` is the row returned by `Store.UpdateUserPassword` (which already clears the flag in SQL). The SPA reads `result.user`, calls `currentUser.set(result.user)`, and navigates to `/`.
- **Files modified:** internal/server/api/local_auth_handlers.go
- **Commit:** 7aaf3eb
