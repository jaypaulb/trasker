<threat_model>
## Trust Boundaries

- **X11 server → daemon (cgo):** untrusted property data (window titles, class hints) crosses into Go. C strings could be malformed or oversized.
- **daemon process → local SQLite file:** trusted (same UID, same fs). WAL mode default.
- **daemon → server HTTPS:** authenticated channel via API key. JSON payload crosses the boundary.
- **screen-lock signal channel → capturer:** trusted (same process), but `<-chan` could be nil (listener unavailable) — must handle.

## STRIDE Threat Register

- **T-7-02-01 — Spoofing:** A rogue X11 client could set arbitrary `_NET_WM_NAME` on a window it doesn't own. Disposition: accept. Rationale: the snapshot is informational ("what was on the desktop"); we record what X11 reports. Mitigation in 07-04-PLAN: dashboard shows raw title (no HTML rendering) so XSS-style payloads don't escape.
- **T-7-02-02 — Tampering:** Window title/app_name strings from cgo could exceed Go string capacity or contain NUL bytes. Disposition: mitigate. Mitigation: `strncpy` into fixed 512-byte buffers in C (matches tracker_linux_x11.go Pattern S from 07-PATTERNS.md), then `C.GoString` in Go (stops at first NUL — well-defined behavior).
- **T-7-02-03 — Repudiation:** Out of scope for client-local data; user owns their own machine and SQLite.
- **T-7-02-04 — Information disclosure (privacy invariant — D-16):** Adding ANY field to Window beyond the 6 (PID, cmdline, exe path, screenshot, focused-flag, z-order) leaks more than authorized. Disposition: mitigate. Mitigation: explicit grep gate in Task 1 + Task 2 acceptance criteria; struct frozen at 6 fields; checker rejects extension. Privacy is a one-way door.
- **T-7-02-05 — Information disclosure (log leakage):** WARN logs containing window titles could leak sensitive URLs/file paths to log aggregators. Disposition: mitigate. Mitigation: sync.go logs only hash + count, never the windows array. Capturer logs enum errors but not window content. Acceptance criterion explicitly grep-checks this.
- **T-7-02-06 — Denial of service:** Misconfigured X11 (DISPLAY unset, libX11 missing) causes capturer to log WARN every 60s indefinitely. Disposition: mitigate. Mitigation: capturer logs the first failure at WARN, subsequent failures at DEBUG (or every Nth — implement a simple counter); RESEARCH.md Open Question #4 recommendation.
- **T-7-02-07 — Denial of service:** Capturing 256+ windows per tick could bloat SQLite. Disposition: accept. Rationale: 256 is the C-side cap; realistic max is ~50; row size ~10KB max; 1440 ticks/day × 7d = 10MB/week ceiling. Negligible.
- **T-7-02-08 — Elevation of privilege:** N/A — capturer runs in user-space daemon with no setuid bits.
- **T-7-02-09 — Spoofing (server-side):** A man-in-the-middle could intercept the POST. Disposition: mitigate by HTTPS (Phase 8 ships autocert TLS); accepted for Phase 7 dev where http://localhost is used.
</threat_model>
